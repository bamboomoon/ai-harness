# 风格：核心原则与模块 CONVENTIONS

原则本身不改变模型的行为——模型早已熟悉 Clean Code。改变行为的是：经典术语作引导词、本仓库的正反例、lint 与独立审查。所以风格只落在两处，都属于项目、都会被 agent 读到，不做成需要自行加载的 skill：

| 放哪 | 写什么 | 怎么保证被读到 |
| --- | --- | --- |
| 模块 AGENTS「核心原则」 | 跨语言引导词与约定（见 [docs.md](docs.md)），加一两行本语言要点 | 进入模块时自动加载 |
| 模块 `CONVENTIONS.md` | 按主题分节：通用规则在前，本仓库的类型、函数、路径、错误码、流程与正反例在后 | 根与模块 AGENTS 的必读提示；可选的编辑前 hook 强制 |

判断一条内容放哪：跨语言的原则或约定 → 各模块 AGENTS「核心原则」（各模块同步）；某个模块的写法（包括语言用法）→ 该模块 CONVENTIONS。

## 从模板生成

[../assets/style/](../assets/style/) 按语言提供起点（`go.md`、`typescript.md`、`java.md`；其他语言照同样结构写）：
1. 「语言要点」压成一两行，并入模块 AGENTS 的「核心原则」；
2. 其余各节并入 CONVENTIONS 的对应主题，改写成项目实际的类型、函数与路径，每条补本仓库正例（`文件` 的 `函数`），反例注明来源（哪次纠正）；项目没有的主题删掉，项目特有主题（如设计稿、UI 组件）另加；
3. 与现有代码冲突的条目按下方「维护」处理。

完成标准：CONVENTIONS 没有「项目的」「如」这类模板措辞，每条规则都能在仓库里找到正例；参考 [../assets/conventions/](../assets/conventions/)。CONVENTIONS 超过约 150 行时按主题拆到模块 `docs/conventions/`，CONVENTIONS 保留索引。

## 引导词（跨语言）

单一抽象层级（编排函数每步一行，带判断的步骤抽成意图命名的函数）、Stepdown（主流程在上，辅助在首个调用者之后）、SRP（写成本模块的分层）、DRY（按知识与变化原因判断）、YAGNI、迪米特、CQS、意图命名（what 由命名与结构表达）。用经典术语而不是长句转述，才能调动模型已有的理解。

## 注释

注释只写 why（动机、约束、取舍、踩过的坑）并附 issue 链接；不写 what。agent 写的 what 注释烂得最快，十有八九是在给短期 hack 找补。
这条与存量代码通常冲突（每个函数一行复述式注释很常见）：规则立即生效，存量按「改到就清」处理，并由独立审查检查。

## 维护

- 每条规则配本仓库正例，注明来源（哪次纠正或实验）；能 lint 的写成 lint 后删除规则。
- 规则与现有代码冲突时，先改代码或暂不写规则——agent 跟随代码而不是规则。
- 反例与正例成对出现：正例说明目标写法，反例记录 agent 实际犯过的错；只写原则时 agent 仍会重犯。
- 交付前独立审查（Claude Code `code-review`、Codex `/review`）以模块 AGENTS 的核心原则与 CONVENTIONS 为标准。
- 定期对规则做删除测试：去掉后行为不变的是 no-op，删除。
- 多个项目都需要的通用写法，回到 agent-harness 修改 `assets/style/` 模板；已生成的项目按需自行同步。
