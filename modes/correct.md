# correct：把一次纠正落成持久的改进

输入：用户对 agent 代码或做法的一条纠正。每一步达到完成标准再进入下一步。

1. **复述纠正**：写成一句可判断对错的规则（「HTTP 入参只用 binding 标签校验」，而不是「代码要干净」），并找出触发它的具体代码。
   完成标准：规则能用一个正例和一个反例说明。
2. **追根因**：为什么 agent 会这样写——仓库里有同样的坏样例？规则藏在 agent 没读到的地方？工具缺失（例如找不到代码生成器而手写生成代码）？
   完成标准：指出根因所在的位置（文件、文档或环境）。
3. **选最高一层落地**：
   - 代码本身：修掉或删除会被模仿的样例；
   - 静态检查：能表达为 lint（依赖方向、复杂度、声明顺序）、类型、测试或 CI 的，写成检查，并确认它能拦下当初的错误；
   - 规则：每次都必须知道、代码里推断不出的约定。先判断适用范围：只在某模块成立（提到本仓库的类型、函数、路径、错误码或流程）→ 该模块 `CONVENTIONS.md` 的对应主题，配本仓库正例、反例注明来源；跨模块 → 根 AGENTS；
   - skill：某类任务特有的步骤；
   - 风格指南：换一个同技术栈的项目仍成立的通用写法，改 agent-harness 的 readable 基线再同步到项目。
   完成标准：新的检查或文档已经生效，且拿当初的错误验证过会被拦下或被引导到正确写法。
4. **清理下层**：规则被 lint 或测试接管后，删掉文档中的对应描述；规则与现有代码冲突时，先改代码或暂不写规则（agent 会跟随代码）。
5. **汇报**：说明纠正落在哪一层、改了哪些文件、如何验证有效。

注意：agent 常常只满足规则的字面意思（例如把被 lint 禁止的导入挪到恰好豁免的文件里）。审查修复时对照规则的意图，并把绕过方式补进规则或检查。
